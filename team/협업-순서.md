# 제출까지 협업 순서

2026-11-06. 기존 담당과 마감은 공유 업무표를 따른다. 아래 순서는 다른 담당자의 일을 대신 수행하거나 새 기능을 확정하는 지시가 아니다.

## 먼저 함께 진행

| 담당 업무 | 지금 할 행동 | 넘길 자료 | 받는 업무 |
|---|---|---|---|
| 화면 C1·T7 | 각자 화면 안을 만든 뒤 차이와 추천안을 정리 | 주차·주행 화면 안, 적용 이유 | 앱 S13 |
| 보상 C2 | 깃털 적립·사용·배지 조건의 안을 정리 | 조건표 한 장; 제안과 확정 구분 | 앱 S12 |
| 기획 T5 | 현재 앱과 기획서 대조, J3 국어 근거 반영 | 접수양식 개정안, 남은 확인점 | 확인 담당 → 제출 |
| 앱 S5·S17 | 새 수업·탐색을 에뮬레이터에서 확인, Gleo 실제 호출 확인 | 성공·실패 경로와 화면 | S8·S9 |
| 점검 T6 | 현재 파일·영상·APK의 실명·계정 노출 확인 | 위치와 수정 필요 목록 | 공개 방식 S7 |

N1 한 줄 소개는 보류한다. 이를 기다리며 초안·음원·통합을 멈추지 않는다. N3 팀·프로젝트 이름은 제출 파일명과 신청서에 필요하며, 이미 발송한 T3 문의를 다시 막는 조건이 아니다.

## 자료가 오면 이어서 진행

1. C1·T7 → S13: 앱 담당이 화면 안을 받아 선택·적용한다. 현재 구현된 재생 진행바·구간 이동을 고려한다.
2. C2 → S12: 이름 깃털·잇찌는 확정 상태다. 사용처·배지는 제안서를 받은 뒤 정한다.
3. 시연 각본·L5 음원 → S8: 최신 앱과 장면·문구를 맞춘 뒤 녹화·편집한다. L5 제작 완료와 영상 완료를 구분한다.
4. T6 → S7: 노출 목록을 보고 저장소 공개 방식을 정한다. 통합·백업을 노출 점검 완료로 기록하지 않는다.
5. N3·S7·최종 코드 → S9: 최종 이름으로 제출용 APK를 다시 빌드하고 검사해 Releases 주소를 만든다. 개발 APK 성공은 이 단계의 완료가 아니다.
6. T5·개인정보 문단·S8·S9 → S10: 제출 자료와 접근 가능한 링크를 확인한 뒤 담당자가 메일을 보낸다. 발송 전에는 제출 완료로 쓰지 않는다.

## 대본과 음원 협업

대본 담당이 CSV와 바뀐 조각 ID를 전달 → 음원 담당이 바뀐 조각만 제작하고 길이·누락 검사 → 앱 담당이 통합·빌드한다. 대본 내용 검토·음원 품질 청취는 현재 프로젝트 업무에서 제외한다(2026-11-06 사용자 결정). 확인할 것은 파일 누락·재생·멈춤·이어 듣기·구간 이동·도착 시간에 맞춘 진행 등 기능 동작이다. 대사가 바뀌면 해당 음원을 맞춰 다시 만든다.

동백꽃 `team/b` 검토안·짧은 판은 현재 `lessons/동백꽃.csv`와 별개 제안본이다. 파일이 main에 합쳐졌다는 이유로 앱 적용본이나 음원을 바꾸지 않는다. 기존 품질 확인 이력은 보관하되, 추가 내용 검토·품질 청취를 필수 후속 일로 만들지 않는다.

## Git과 업무표 기록

1. 담당자는 깨끗한 작업 폴더에서 `git fetch origin`, 최신 main 갱신 후 `codex/업무번호-짧은설명` 브랜치를 만든다. 미커밋 변경이 있으면 먼저 보존한다.
2. 기존 작업 브랜치를 계속할 때는 main을 먼저 병합해 차이를 확인한다. 예전 team-base를 공동 최신본으로 안내하지 않는다.
3. 결과물·변경 이유·검사 결과·남은 일을 함께 전달한다. 앱 코드는 앱 담당이 확인하고 통합한다. 이번 전체 통합은 사용자의 명시적 요청에 따른 공동 정리다.
4. 원격은 main 포함 최대 5개만 유지한다. 통합 전 백업은 태그로 남기고, 검사·일반 푸시 후 main에 포함된 작업 브랜치는 삭제한다. 미통합 작업과 사용 중인 로컬 작업 폴더는 먼저 보존한다. main 강제 푸시는 하지 않는다.
5. 업무표 메모는 `날짜 / 끝낸 범위 / 결과물 / 검사 / 다음 인계`로 짧게 갱신한다. 상세 로그는 셀 메모·결과물에 둔다. 같은 사실을 수업·결정·보관 탭에서도 맞춘다.

끝남은 해당 행에 적힌 범위의 완료다. 대본 초안·AI 검토·사람 검수·음원 제작·앱 통합·발송을 서로 대신 표시하지 않는다.
